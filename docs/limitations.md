# 已知限制（Weixin 4.1.13.65，PHASE 6）

## 检测（PHASE 1）

| # | 限制 | 原因 | 实际表现 / 应对 |
|---|---|---|---|
| 1 | **托盘状态没有消息正文** | 窗口隐藏时 Qt 的 UIA 桥跳过不可见控件，微信也会把预览从会话单元的 Name 中去掉 | 报告「会话名 + 未读数」（`SessionMetadata`）。想要正文就用「—」最小化代替「×」，最小化时内容完整可读 |
| 1a | **微信窗口停在「发现」「通讯录」等页时，同样没有消息正文**（2026-10-02 你发现的） | 聊天列表不在屏幕上，会话单元的 Name 和托盘时一样只剩会话名和未读数，文字不在任何读得到的地方 | 和托盘一样报告「会话名 + 未读数」；切回聊天列表后，下一条消息恢复正文，点击通知会切到对应会话。程序不会自己把微信切回聊天页：那会打断你正在看的朋友圈或通讯录 |
| 2 | 微信启动后从未打开过主窗口时，什么都读不到 | 没有机会捕获元素引用 | 立即报告通用「微信 · 新消息」；用户第一次打开主窗口后恢复正常 |
| 3 | 预览会被截断 | 微信按会话列宽截断预览（以 `…` 结尾） | 该会话在窗口中打开且可见时，从消息列表读取全文；否则显示截断后的预览 |
| 4 | 同一会话在一次读取前连续到达多条消息，只能拿到最后一条的文字 | 会话列表只显示最后一条 | 事件带 `NewMessages`（未读增量），不会漏掉会话；0.7.0 起通知里在最后一条上面列一行「[n 条新消息]」，表示中间有几条读不到内容 |
| 4a | 未读数变小（但不是 0）按新消息报告（0.6.4） | 程序只在收到闪烁时读会话列表；你在手机上读过（电脑上的未读数回到 0，不闪烁）之后对方再发，看到的是「3 → 1」 | 以前只弹通用「新消息」，现在带会话名和头像。代价：未读消息被撤回也会让未读数变小——微信可见时预览是「撤回了一条消息」，能认出来；在托盘时看不到预览，这种少见情况会多一条「新消息」 |
| 5 | 打开中的会话连续收到**完全相同**的文字（同一分钟内） | 预览和时间都没变，差分看不到变化 | 仍然有闪烁 → 1 秒后报告通用「新消息」 |
| 6 | 托盘状态下打开中的会话收到消息 | 该会话的未读数可能不增加，预览又被隐藏 | 1 秒后报告通用「新消息」，并附「可能来自：当前打开的会话」提示 |
| 7 | 群聊发送者暂不解析 | 按你的要求先不处理群聊（PHASE 3） | 群消息显示为「群名 + "发送者: 内容"」，这正是微信自己的预览格式 |
| 8 | 置顶会话多于可见行数时，新消息会话可能不在可见行中 | 会话列表只包含可见行 | 1 秒后报告通用「新消息」 |
| 9 | 「微信在前台时也通知」目前基本无效 | 微信在前台时不闪烁，也就没有触发信号 | 默认关闭（符合规格 §15）；需要时再加前台专用触发器（PHASE 5） |
| 10 | 依赖微信闪烁任务栏按钮 | 这是主触发信号 | 如果用户关闭微信的新消息提醒、或微信改变此行为，就收不到触发；诊断页会显示「最后一次触发时间」 |
| 11 | 两个会话显示名完全相同 | 状态按显示名区分 | 两者可能互相干扰；点击通知时不会跳转到重名会话（只把微信带到前台） |
| 12 | `RegisterShellHookWindow` 被 MSDN 标注为「不适合一般用途」 | 但它自 Windows 2000 起一直稳定，且是唯一能收到跨进程闪烁通知的公开 API | 通过 `TaskbarCreated` 在 Explorer 重启后重新注册 |
| 13 | 延迟按最近一次闪烁计时 | 微信每条消息闪烁约 4 次，无法确定哪次闪烁属于哪条消息 | 正常情况下与真实延迟相同；如果微信在第二次闪烁（≥310 ms）之后才更新列表，报告的数字偏小 |

## 通知（PHASE 2）

| # | 限制 | 原因 | 实际表现 / 应对 |
|---|---|---|---|
| 14 | 需要 Windows App Runtime 2.5.1 以上（框架包、Main、Singleton、DDLM，微软的运行时安装程序装的就是这四个） | 采用依赖框架的部署；`AppNotificationManager` 本身依赖 Singleton 包 | 0.8.0 起安装程序自带这些包，缺少时为当前用户装上。直接运行构建目录里的程序（开发）时要自己装；缺失时后台程序会说明原因，控制台宿主只输出到控制台 |
| 15 | 通知中心每个会话只保留一条（最新消息 + 未读数） | 有意为之：连发 10 条时只更新一个横幅，不堆 10 个 | 之前的消息已作为横幅显示过；完整内容在微信里 |
| 16 | 横幅出现的时间点 | Windows 只报告「已交给通知平台」，不报告「已画到屏幕上」 | 性能数据测的是闪烁 → `Show()` 返回；之后的动画由 Windows 完成 |
| 17 | 以管理员身份运行时没有通知 | Windows 不显示来自提升权限进程的通知 | 控制台显示原因；不要以管理员身份运行 |
| 18 | 勿扰 / 专注模式下没有横幅 | 规格 §16：尊重 Windows 设置 | 通知直接进入通知中心 |
| 19 | 点击跳转会话只对**可见行**里、名字唯一的会话有效 | UIA 只能找到可见的会话单元；微信 4.1 不响应会话单元的 UIA Invoke/Select（0.6.2 及以前跳转从未成功），所以 0.6.3 起像用户一样单击那一行 | 只在微信是前台窗口、那一行看得见、没有别的窗口挡着时单击，鼠标指针随后回到原处；找不到、不能安全单击或核实失败时只把微信带到前台（规格 §27：稳定性优先）。日志 `not clicking: …` 写明原因 |
| 20 | 托盘状态下点击通知，靠点击微信的**托盘图标**来显示窗口 | 再次启动 `Weixin.exe` 会打开第二个登录窗口（微信 4 支持多开，你在 PHASE 2 测试中遇到）；从外部对隐藏的 Qt 窗口调用 `ShowWindow` 会让 Qt 的状态错乱 | 通过 Windows 外壳的 UI Automation 点击托盘图标（图标在「显示隐藏的图标」里时会短暂展开那个弹出框）。前提：微信的托盘图标存在且只有一个；多开时不点。Windows 改变任务栏结构后用 `WeChatInspector trayprobe` 检查 |
| 21 | ~~PHASE 2 中通知的激活服务器是控制台宿主~~ | PHASE 4 已解决 | 激活服务器是最后一次启动的程序：平时是 `WeChatNotifier.exe`（无窗口）。运行一次控制台宿主后，它会把注册改指向自己，直到 App 再次启动 |
| 22 | 同一用户会话只能运行一个宿主 | 两个宿主会让每条消息出现两次 | App 和控制台宿主共用一个命名 Mutex：再次启动 App 只会让运行中的那个提示「已经在运行」 |

## 头像、群消息、图片（PHASE 3）

| # | 限制 | 原因 | 实际表现 / 应对 |
|---|---|---|---|
| 23 | 真头像需要微信窗口**在屏幕上出现过** | 头像只能从屏幕复制（UIA 不给像素）；最小化/托盘时没有画面 | 你在微信里停留过 1.5 s 后，可见会话的头像会被记住，0.6.2 起程序重启后也记得（保留 30 天）；从没在屏幕上见过的会话用首字头像。0.6.1 及以前：每次重启（更新、开机、「重新启动监听」）都会忘掉全部头像，微信一直最小化或在托盘时就全是首字头像 |
| 24 | 头像位置是按比例算出来的 | 会话单元没有头像子元素 | 规则在 `WeChatUiProfile.SessionAvatar`；微信改版后先跑 `WeChatInspector captureprobe` 检查（复制结果是纯色就自动退回首字头像） |
| 25 | 图片预览只在「该会话正打开（主窗口或独立聊天窗口）、窗口在屏幕上（可被遮挡，但不能最小化）、消息列表停在最底部」时有 | 只有这时新图片的气泡在画面上；程序不会替你在微信里切换会话（只读原则），也不读微信的本地图片文件（加密，属于规格的 Level 4）。列表往上翻着时，最下面看得到的是旧消息——宁可不带图，也不拿旧图片冒充 | 其他情况显示「[图片]」，日志写明原因（别的会话 / 最小化或托盘 / 列表没在底部 / 还在加载）。0.6.0 及以前：会话正打开时也常常没有预览——程序读的是之前记下的消息列表引用，微信换过聊天页后它什么也读不到（日志 `the newest visible message is not this picture`）。0.6.1 起每条图片消息都重新读一次当前聊天页 |
| 26 | 会话正打开时，图片消息的通知最多晚约 1.5 秒 | 微信要先把新气泡排到列表底部，先显示灰色占位，再下载缩略图 | 每 200 ms 再看一次，图片出现就带图通知；1.5 秒后仍没有就只写「[图片]」，日志写最后看到的情况。你最小化微信、切到别的会话或关掉独立聊天窗口时立即停止等待。只有「会话正打开且在屏幕上」的图片消息会等；其他消息照常立即通知 |
| 27 | 群消息的发送者来自预览文字 | 消息单元的 UIA Name 不含发送者 | 正文就是微信自己的「发送者: 内容」；私聊里以「词: 」开头的消息在控制台会被当成发送者标签，通知内容不受影响 |
| 28 | 托盘状态的群消息没有发送者 | 托盘时预览不可读（#1） | 只有「群名 / 新消息」 |

## 后台程序（PHASE 4）

| # | 限制 | 原因 | 实际表现 / 应对 |
|---|---|---|---|
| 29 | 托盘右键菜单始终是浅色 | Win32 弹出菜单只有通过未公开的 uxtheme 函数才能变深色，规格要求优先公开 API | 菜单只剩 6 项；设置都在设置窗口里，它（WinUI）和通知都跟随深色/浅色模式 |
| 30 | 托盘图标默认在「显示隐藏的图标」（^）里 | Windows 11 对新图标的默认做法，程序不能自行改变 | 把图标拖到任务栏上，或在「设置 → 个性化 → 任务栏 → 其他系统托盘图标」里打开 |
| 31 | 微信在托盘时「重新启动监听」或程序重启，会话名要等微信打开一次后才恢复 | 同 #2：新的 Listener 只能在窗口可见时取得会话列表引用 | 改设置**不会**重启 Listener（选项在运行中替换）；只有菜单里的「重新启动监听」和崩溃后的自动重启会这样 |
| 32 | 「暂停通知」不跨重启保存 | 有意为之：重启或重新登录后通知总是开着，不会忘记恢复 | 暂停期间的消息数在恢复时提示 |
| 33 | 「群聊消息」开关靠预览格式识别群聊（PHASE 5） | UIA 没有群聊标志；唯一的线索是预览里的「发送者: 」 | 关闭开关时：带「发送者: 」的消息、以及本次运行见过两个不同发送者的会话不再通知。私聊消息本身以「词: 」开头（#27）时那一条也会被当成群消息；托盘状态下没见过两个发送者的群仍会通知。开关默认开，开着时不受影响 |
| 34 | 开机启动指向登记它的那个 exe（现在是构建目录） | Run 键里是完整路径 | 程序被移动、原路径不存在时，下次启动会自动改正；PHASE 6 的安装程序把它放到固定位置。任务管理器里禁用后，程序不会自己重新打开 |
| 35 | Listener 重启的那几十毫秒里点击通知不会生效 | 新旧 Listener 交接时没有可用的 Listener | 日志记一行 `notification clicked while the listener restarts`；再点一次即可 |
| 36 | 登录后的头几秒可能还没有托盘图标 | 任务栏还没创建时 `Shell_NotifyIcon` 会失败 | 等 Explorer 广播 `TaskbarCreated` 后自动添加；通知不受影响 |

## 头像、设置窗口、安装（PHASE 5–6）

| # | 限制 | 原因 | 实际表现 / 应对 |
|---|---|---|---|
| 37 | 头像边缘和列表背景几乎同色时，按像素找不到头像 | 找头像靠「与背景不同」的像素块 | 用上一个找到的头像位置（同一布局），从没找到过就用估计比例 0.56；最坏情况是头像带一点边。0.7.1 起，中间一半几乎全是列表背景色的复制结果不算头像（防止错位截图），所以几乎纯白、只有很小标志的头像会显示成首字头像 |
| 38 | 收到消息时复制的头像可能带着未读角标的一角 | 角标压在头像右上角 | 先用着，你读过之后（角标消失、微信在屏幕上时）自动换成干净的；圆形裁剪本身也去掉了大部分角标 |
| 39 | 设置窗口打开时约占 190 MB 内存 | WinUI 3 本身的开销 | 它是单独的进程，关掉窗口就完全释放；后台程序始终约 60 MB |
| 40 | ~~安装需要 .NET 10 运行时和 Windows App Runtime 2.5.1+~~ | 0.8.0 已解决 | 安装程序自带两者：.NET 运行时在程序文件里（自包含发布），Windows App Runtime 缺少时从 exe 里装上，不联网。代价是安装包约 91 MB（以前约 10 MB），装好后约 113 MB。卸载时 Windows App Runtime 保留：它是系统共用的组件，别的应用可能也在用 |
| 41 | 安装程序没有数字签名 | 个人工具，没有代码签名证书 | 第一次运行时 SmartScreen 可能提示「未知发布者」→「更多信息」→「仍要运行」。安装包的 SHA-256 在构建时打印，可以核对 |
| 42 | 只支持 x64 | 当前只发布了 win-x64 | ARM64 电脑需要另外发布一份（项目已列出 win-arm64，PHASE 6 之后再说） |
| 43 | 通知里的头像、图片和标题栏图标按**主显示器**的缩放比例生成 | Windows 只按原尺寸画得清晰；别的尺寸它用简单滤镜缩放，圆边会出锯齿（0.6.6 及以前） | 通知总是出现在主显示器上，所以通常正好。运行中改了主显示器的缩放：头像和图片从下一条通知起跟着变，标题栏图标要等下次登录 Windows（Windows 在一次登录期间一直用它最先读到的图标文件，程序重启也不会让它换）。缩放超过 300 % 时标题栏图标用最大的 48 px，会被 Windows 放大一点 |
| 44 | 通知里较早的消息每条只占一行，按**估计**的宽度截断 | Windows 的通知正文合计最多 4 行，超出的直接丢掉、不加「…」，也不理会限制行数的提示；前面一条换行就会把最新一条挤出去 | 程序按字符宽度估计（汉字 14 有效像素，一行约 18 个汉字）提前截断并加「…」，留了余量，所以有时比实际能放下的少一两个字。英文按单词换行，估计偏乐观：很长的英文最新消息可能仍被 Windows 在第 4 行末尾直接截断。微信在托盘时读不到内容，那几条只显示成「[n 条新消息]」 |
| 45 | 「以『微信』的名义显示」的更改要等**下次登录 Windows** 才看得到 | Windows 每次登录只读一次通知的应用名和图标，之后一直用它（2026-10-02 实测：改了注册表里的名称，通知标题照旧） | 设置窗口里有说明。打开后，「设置 → 系统 → 通知」的应用列表里本程序也显示为「微信」（电脑上的微信本身不用 Windows 通知，所以不会有两个）；托盘图标和设置窗口仍叫 WeChat Notifier。微信的图标从电脑上的 `Weixin.exe` 读取；从没找到过微信时先用本程序的图标 |

PHASE 0 的完整证据见 [wechat-ui-analysis.md](wechat-ui-analysis.md) §4–§5。
