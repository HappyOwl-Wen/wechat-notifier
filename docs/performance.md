# 性能（实测）

测量环境：Windows 11 Pro 10.0.26300，16 逻辑核，Weixin 4.1.13.65，.NET 10.0.12 运行时，Windows App Runtime 2.5.1，Release 构建。「单核 %」= CPU 时间 / 墙钟时间。

## 通知延迟分析（2026-10-01 的真实消息，0.5–0.6.4）

从日志里 87 条「未读数增加」的消息和 92 条消息通知统计：

| 环节 | 中位数 | p90 | 最慢 |
|---|---|---|---|
| 闪烁 → 检测到（读会话列表） | 168 ms | 317 ms | – |
| 组装 + 交给 Windows（build+show） | 100 ms | 179 ms | 360 ms |
| 闪烁 → 通知交给 Windows | 275 ms | 449 ms | 1094 ms（唤醒后第一条） |

- 检测时间按读取时间点成簇：45 条在 +150 ms 那次读取被看到（160–199 ms），约 20 条要等到 +300 ms 或之后（250–400 ms）——微信在闪烁后 150–300 ms 才更新会话列表。0.6.5 加了 +100 和 +210 ms 两次读取。
- 最慢的几条通知（220–360 ms build+show）都是文字消息、头像文件已存在、没有图片：时间花在 Windows 的 `Show()` 上（通知平台在另一个进程里写自己的数据库），而且多数是同一会话的第二条、替换了还在的上一条。0.6.5 起日志把 files / build / show 分开记录，并记下是否替换（`replaces=`），用来确认。
- 检测到之后到开始组装通知：中位数 0 ms，p90 6 ms（通知线程偶尔还在处理上一条或撤回）。

## PHASE 1 控制台原型

| 指标 | 结果 | 目标（规格 §10） |
|---|---|---|
| 空闲 CPU（附着微信、无新消息） | 附着后第 92–153 s 之间：**0 ms**（进程被阻塞，无任何唤醒）<br>15 分钟整体（含附着和首次捕获）：125 ms = **单核 0.014%** | 接近 0%，长期 < 0.5% |
| 启动 + 附着 + 首次捕获 | CPU ≈ 170 ms（主要是 JIT）；附着 60 ms，捕获 10 个会话单元 37 ms | – |
| 空闲内存 | 工作集 38.5–40.3 MB（15 分钟后峰值 40.3 MB），私有内存 8.7 MB；16 个线程，382 个句柄 | 工作集 < 100 MB |
| 一次触发（burst）的读取 | 6 次读取，完整 burst 约 1.5 s；可见状态单次读取 3–15 ms，托盘状态约 1 ms/单元 | 允许短时 CPU spike |
| 触发 → 检测（你的实测，01:28–01:31） | 可见 314 ms，最小化 164–166 ms，托盘 311–314 ms，图片 309 ms | < 500 ms |
| 网络 | 0 个 TCP 连接，0 个 UDP 端点，未加载 ws2_32/winhttp/wininet/System.Net | 不得联网 |

你在 PHASE 1 实测中连发消息时，日志里的延迟从 2.4 s 一路涨到 11.5 s。那是计时方式的问题：当时按整个 burst 的第一次闪烁计时，而连续消息让同一个 burst 持续了 11 秒。PHASE 2 改为按每条消息自己的（最近一次）闪烁计时；检测本身并没有变慢（unread 计数逐条 +1，没有合并或遗漏）。
